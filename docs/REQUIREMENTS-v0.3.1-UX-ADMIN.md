# LiveBlog Sphere v0.3.1 产品体验修复与后台管理重构需求说明书

- 文档版本：1.0.0
- 状态：待评审 / 待实施
- 目标版本：v0.3.1
- 基线：v0.3.0 本地演示版
- 产品阶段：优先修复现有功能、交互缺陷和可用性问题；本版本不引入新的业务模块
- 适用对象：产品负责人、开发、测试、后续维护人员

## 1. 项目目标与原则

### 1.1 本阶段目标

1. 将后台文章管理从“全部文章纵向堆叠”调整为适合持续增长的内容管理工作台。
2. 修复首页搜索筛选、分类导航、热门标签等看起来可点击但没有行为的控件。
3. 为所有交互补齐加载、成功、失败、空状态和危险操作确认反馈。
4. 建立可持续维护的项目说明、架构说明、版本变更记录、提交说明和测试报告。
5. 保证本地演示与未来 Supabase 正式环境边界清楚，不把本地模拟认证误当作生产安全能力。

### 1.2 设计原则

- 先修复再扩展：v0.3.1 不新增消息、支付、推荐算法、复杂工作流等业务模块。
- 可发现：可交互元素必须有明确文案、按钮语义、hover/focus 状态和键盘操作。
- 可反馈：操作后必须给出成功/失败反馈；异步操作展示 loading。
- 可恢复：删除优先进入回收站/软删除；永久删除必须二次确认。
- 可扩展：文章列表采用分页/排序/筛选，不一次性渲染全部记录。
- 权限可信：前端角色判断只负责展示；正式环境权限必须由 Supabase RLS/服务端校验。
- 文档同步：每次代码变更都同步更新 CHANGELOG、必要的架构/使用文档和 PR 描述。

## 2. 现状与问题证据

### 2.1 管理后台

当前管理页将所有文章直接渲染为纵向列表，每条文章提供查看、编辑、删除。页面缺少：
- 搜索标题/摘要/正文；
- 状态、作者、分类、标签、时间范围筛选；
- 排序、分页、每页条数；
- 多选与批量操作；
- 回收站和恢复；
- 更清晰的文章状态、更新时间、作者、分类等字段；
- 筛选条件下的结果数与空状态。

当文章达到数百或数千篇时，长列表会增加定位成本和首屏渲染成本。当前“用户数量”和文章列表数据均来自本地演示存储，不代表云端真实统计。

### 2.2 首页控件

代码检查确认：
- `src/components/home/Sidebar.tsx`：快速导航的“首页”和分类项使用静态 `div`，没有链接或点击事件。
- 同文件：热门标签使用静态 Badge，没有点击筛选行为。
- 同文件：访问说明是静态说明文字，不是操作控件；应明确其为说明内容，避免呈现成可点击入口。
- `src/components/home/Banner.tsx`：搜索框旁 Filter 按钮只有图标和 aria-label，没有 onClick、弹层或筛选逻辑。
- `src/pages/Index.tsx`：当前搜索只匹配标题与摘要；没有分类/标签/状态/时间的组合筛选。

### 2.3 项目文档

当前 README 仍保留 Lovable 初始模板内容，技术栈说明不完整，未充分说明真实项目边界、目录结构、运行方式、演示账号、数据持久化方式、已知限制和版本流程。需要替换为项目自己的维护文档。

## 3. 产品调研与设计依据

本需求参考成熟内容管理产品的通用交互模式：

1. **WordPress Posts Screen**：使用表格行管理文章，提供状态视图、搜索、日期/分类筛选、可排序列、分页、选择框和批量操作；支持快速编辑。适合借鉴为本项目后台文章列表的基础模式。
   - https://wordpress.org/documentation/article/posts-screen/
2. **Ghost Admin 内容管理**：支持按草稿、已发布、精选、访问级别、作者、标签筛选，并可保存常用视图；支持多选批量添加/移除标签、调整访问级别、精选状态和取消发布。
   - https://ghost.org/help/organizing-content/
   - https://ghost.org/changelog/bulk-actions/
3. **Directus Content Layouts**：默认表格布局，允许调整列、排序、选择多条记录；也提供卡片等不同布局。说明列表布局应围绕数据字段和任务效率，而非把每条记录做成大块纵向卡片。
   - https://directus.com/docs/guides/content/layouts

### 3.1 本项目采用的模式

采用 WordPress 的“表格管理 + 筛选 + 分页 + 批量操作”作为主框架，吸收 Ghost 的状态/作者/标签筛选和保存视图思想，但 v0.3.1 先实现基础筛选，不做复杂的自定义视图系统。文章卡片仅保留在访客首页；后台默认使用紧凑表格。

## 4. 需求范围与优先级

优先级定义：
- P0：阻断核心使用、误操作或明显无效交互，必须在本版本修复。
- P1：显著影响效率和体验，本版本应完成。
- P2：可用性增强；在不扩展业务范围且 P0/P1 完成后实施。

### 4.1 后台文章管理工作台

#### P0 — 列表基本可用性
- 用紧凑表格替换当前无限纵向文章卡片/行列表。
- 默认按最近更新时间或创建/发布时间倒序；字段缺失时使用稳定的创建时间排序。
- 表格列至少包括：选择框、标题、状态、作者、分类/标签、创建/发布时间、更新时间、操作。
- 标题点击进入编辑；“查看”打开访客文章页；操作菜单提供编辑、查看、移入回收站。
- 桌面端表格横向空间合理；窄屏改为紧凑行卡片，操作入口不溢出屏幕。
- 列表必须显示总数、当前页范围、当前页码。
- 加载、空列表、筛选无结果、读取失败分别提供不同状态和恢复操作。

#### P0 — 搜索和筛选
- 支持标题关键字搜索；如果当前模型已有摘要/正文纯文本字段，可追加摘要搜索。富文本正文搜索需先验证数据结构和性能，不得假设全文索引已存在。
- 状态筛选：全部、已发布、草稿、定时发布（仅当当前模型确实支持）、回收站（实现软删除后）。
- 分类筛选、标签筛选、作者筛选（管理员可用）。
- 日期筛选：全部时间、近 7 天、近 30 天、自定义日期范围。
- 支持清除筛选，一键回到默认列表。
- 筛选条件组合生效；搜索输入防抖 250–400ms，避免每个字符触发昂贵查询。
- 当前为 localStorage 数据源时在客户端过滤；切换 Supabase 后改为数据库端过滤/排序/分页，禁止一次性取回全部文章再前端分页。

#### P1 — 排序和分页
- 支持按标题、状态、作者、创建时间、发布时间、更新时间排序；仅对有真实字段的列开放排序。
- 默认每页 20 条，允许选择 10/20/50 条；是否提供 100 条需结合性能验证。
- 分页支持上一页、下一页、首页、末页（数据源可计算时）和当前页显示。
- 搜索/筛选条件改变时自动回到第一页。
- 删除或批量操作后若当前页变空，自动回到前一有效页。
- URL query string 保存 page、pageSize、sort、direction、status、category、tag、author、q，方便刷新、返回和分享（本地 demo 不涉及私密数据）。

#### P1 — 批量操作
- 每行选择框和表头全选当前页。
- 显示已选择数量；跨页选择暂不要求。
- 批量操作至少包括：移入回收站、修改分类/标签（仅在模型支持且实现无歧义时）、发布/取消发布（需符合当前文章状态模型）。
- 批量删除必须显示所选条数并二次确认。
- 执行后反馈成功/失败条数；失败记录保留选择并给出可重试提示。
- 批量操作不允许悄悄忽略无权限记录。

#### P1 — 安全删除与恢复
- 默认“移入回收站”，不直接永久删除。
- 回收站支持恢复；永久删除必须二次确认并明确不可恢复。
- 只有当现有数据模型和 repository 能安全实现软删除时才开发；若无法在不破坏历史数据前提下实现，则本版本先保留单条删除确认，并将回收站列为 P2/后续迁移任务，不得伪造回收站 UI。

### 4.2 首页交互修复

#### P0 — 快速导航
- “首页”链接到首页并清除当前分类/标签筛选。
- 分类项点击后按分类过滤文章，更新结果数和空状态；当前分类有明显选中状态。
- 若分类项很多，保留有限显示或折叠；不得出现无响应的静态文本假按钮。
- 所有链接可通过键盘 Tab 聚焦并通过 Enter 激活。

#### P0 — 热门标签
- 标签点击后筛选对应标签文章。
- 标签选中状态可见；再次点击或点击“清除筛选”可取消。
- 标签数据为空时显示合理空状态，不渲染不可点击的装饰 Badge。

#### P0 — 搜索筛选按钮
- 点击 Filter 图标必须打开筛选 Popover/面板，而不是空按钮。
- 初始筛选项：分类、标签、文章状态（首页访客不显示草稿/管理状态）、发布时间范围、排序方式。
- 访客只查询公开文章；本地 demo 中如存在草稿，不得通过访客首页筛选泄漏。
- 提供“应用筛选”和“重置”两个明确操作；应用后更新 URL 或页面筛选状态。
- 图标按钮增加可访问名称、Tooltip、focus 状态和打开/关闭状态。

#### P1 — 搜索行为
- 搜索至少匹配标题和摘要；正文搜索是否支持需依据 Post 数据模型验证。
- 显示匹配数量和空结果状态。
- 搜索、分类、标签、时间筛选可以组合。
- 清除按钮清空搜索和相关筛选，行为明确。
- 无结果时给出“清除筛选”入口，不只显示“暂无文章”。

### 4.3 访问说明与权限文案

- 当前“访问说明”卡片应明确为静态帮助信息，不使用按钮/链接的视觉样式。
- 角色文案必须与实际权限一致。当前说明写“管理员可以编辑和创建文章”，但产品规则是作者管理自己的文章、Editor/Admin 管理全站；应更新为：
  - 访客：浏览和搜索公开文章。
  - 登录用户：创建、发布、编辑和删除自己的文章。
  - 编辑：管理全站文章（具体删除权限由最终权限矩阵确定）。
  - 管理员：管理全站内容和用户。
- 本地演示角色仅用于本机体验，不能在文案中暗示为安全的正式权限。

### 4.4 用户管理与后台结构

- v0.3.1 暂不重做完整用户管理模块，但将用户列表与文章管理分区/导航清楚。
- 用户角色修改、删除用户等危险操作必须二次确认，并展示结果。
- 管理员不能删除自己或其他系统管理员（除非未来明确设计超级管理员转移流程）。
- 本地演示数据与云端用户统计必须明确区分。

## 5. 后台信息架构建议

建议后台采用左侧导航 + 顶部工具栏 + 主内容区：

- 概览：文章数量、草稿数量、待处理内容（仅展示真实存在的数据）。
- 内容管理：
  - 全部文章
  - 已发布
  - 草稿
  - 定时发布（模型支持时）
  - 回收站（软删除实现后）
- 用户管理：用户列表、角色筛选。
- 系统说明：本地演示环境提示、版本号、数据来源。

首版可先实现单页管理台中的二级导航/状态 Tab，不必立即做复杂多页管理系统。重点是列表工作流和操作效率。

## 6. 当前数据架构与技术约束

### 6.1 当前本地演示技术栈（以仓库配置为准）

- React 18 + TypeScript
- Vite
- React Router
- Tailwind CSS
- shadcn/ui（Radix UI primitives）
- lucide-react 图标
- Framer Motion
- Node.js / npm
- 现有 repository/data 层及浏览器 localStorage/sessionStorage

### 6.2 现阶段数据边界

- v0.3.1 本地体验版：文章、用户等演示数据由本地 repository/localStorage 提供；不同浏览器、不同设备不共享。
- 目标正式架构：Supabase Auth + PostgreSQL + Storage + RLS，作为唯一核心业务数据源。
- 已确认 Supabase 目标项目 ref：`wkywjpjfhpyxffsmmgka`。
- MongoDB Atlas 暂不作为文章/用户的第二份真源；除非未来出现明确的文档型/搜索/分析需求并经评审，不重复保存同一业务实体。
- 正式 Supabase 接入不属于本次体验修复版本，不能在没有 schema/RLS 盘点和项目密钥配置前擅自连接或执行写操作。

### 6.3 分层建议

- UI 页面：展示、交互、状态反馈。
- Hooks / query state：管理筛选、排序、分页和 URL 状态。
- Repository：封装文章列表查询和批量操作，避免组件直接读写 localStorage。
- Data source adapter：当前 local adapter；未来 Supabase adapter。接口应支持 filter/sort/page，不要把全量数组假设写死在 UI。
- Supabase adapter：未来由数据库端执行分页、排序、过滤；权限由 RLS 保证。

## 7. 非功能需求

- 性能：文章列表默认只渲染当前页；5000 条本地演示数据下筛选/翻页交互仍应可接受（以实际测试为准）。
- 稳定性：筛选组合、空数据、缺失字段、异常 JSON、刷新和返回页面不得崩溃。
- 可访问性：按钮有名称；图标按钮有 aria-label；表格可键盘操作；焦点状态清晰；颜色不是唯一状态表达方式。
- 响应式：桌面优先，平板和手机可操作；表格在小屏采用列隐藏/行卡片，不横向挤压主要按钮。
- 安全：开发演示入口仅限 DEV；正式权限不依赖前端角色字段；不得提交 service_role key 或真实用户凭据。
- 数据保护：所有破坏性操作均有确认；优先软删除；不得为了 seed 数据清空现有用户内容。

## 11. 每次提交和发布的强制交付规范

### 11.1 Commit message

采用 Conventional Commits 风格：

- `feat(scope): ...` 新功能
- `fix(scope): ...` Bug 修复
- `refactor(scope): ...` 不改变行为的重构
- `docs(scope): ...` 文档
- `test(scope): ...` 测试
- `chore(scope): ...` 工程维护

### 11.2 每个 PR 必须包含

1. 本次开发了什么。
2. 修复了哪些 Bug（写明复现现象和修复结果）。
3. 修改文件清单及关键设计。
4. 数据结构/迁移是否变化。
5. 测试命令与真实结果（不得把未运行的测试写成通过）。
6. 未完成事项、已知问题和风险。
7. 本地运行/验证步骤。
8. 对应需求编号（如 ADM-001、HOME-002）。

### 11.3 文档维护

- 根目录 README：项目简介、技术架构、环境要求、启动方式、测试方式、目录说明、数据边界和安全警告。
- `docs/ARCHITECTURE.md`：前端分层、数据流、认证现状、目标 Supabase 架构、权限边界。
- `docs/CHANGELOG.md`：按版本记录新增、修复、重构、测试和已知问题。
- `docs/REQUIREMENTS-v0.3.1-UX-ADMIN.md`：本需求及验收基线。
- 任何变更必须在同一 PR 更新对应文档。
